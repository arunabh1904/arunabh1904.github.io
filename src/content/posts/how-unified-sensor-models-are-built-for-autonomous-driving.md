# Perception for Autonomous Driving

Driving perception converts measurements from cameras, LiDAR, and radar into a geometric model of the scene. Each sensor starts with different evidence: cameras capture appearance along image rays, LiDAR returns sparse 3D positions and intensity, and radar measures range and radial velocity with weaker angular resolution. A useful model preserves these differences during encoding, then uses calibration to express the resulting features in a common vehicle coordinate frame.

The shared representation determines what the model can fuse, remember, and predict. A dense bird's-eye-view (BEV) grid retains roads, free space, and weak background evidence. A sparse set of object queries concentrates computation on actors and tracks. LiDAR introduces another distinction: it may be a runtime input, a source of training labels, or part of a teacher model. This survey follows these choices from sensor encoding through geometry, fusion, temporal memory, supervision, and task heads.

## Perception pipeline

The runtime pipeline begins with one encoder per sensor type. Calibration then maps the encoded evidence into a dense BEV field or a sparse set of 3D queries. A temporal module carries that representation across frames, and task-specific heads predict objects, occupancy, lanes, velocity, or planning outputs. The dashed path in the diagram belongs only to training: LiDAR labels, teacher features, and future frames may supervise the model without becoming inputs to the deployed system.

[![Autonomous-driving perception pipeline from sensor-specific encoders through calibrated metric representations and temporal state to task heads, with a separate training-only graph](/assets/images/autonomous-driving-perception-system.svg)](/assets/images/autonomous-driving-perception-system.svg)
_Camera, LiDAR, and radar features become comparable after their coordinates and timestamps are aligned in a metric frame. Fusion then operates in BEV or query space._

Most architectures can be compared with four questions: what survives sensor encoding, how the model assigns a 3D location, where fusion occurs, and what state persists across frames.

## Sensor encoders

### Camera features

A surround-camera system can share one CNN or vision transformer across all views, but each camera has its own image coordinates. For a 3D point $X$, camera $i$ uses its intrinsics and extrinsics to compute the projected pixel $u_i=\pi(K_i,R_i,t_i,X)$. A second camera usually maps the same point to a different pixel. When the backbone returns a feature pyramid, level $l$ must be sampled at the stride-adjusted coordinate $u_i/s_l$. Feature pyramids already existed in 2D detectors such as [EfficientDet](/paper%20shorts/2020/04/01/efficientdet-scalable-and-efficient-object-detection.html). The important step in 3D perception is using calibration to sample those multiscale maps at locations implied by a metric hypothesis.

[![Animation showing one metric 3D point projected to different pixels in two calibrated cameras and sampled at stride-adjusted feature-pyramid coordinates](/assets/images/autonomous-perception-vision-encoder.gif)](/assets/images/autonomous-perception-vision-encoder.gif)
_[DETR3D](/paper%20shorts/2021/10/14/detr3d-multiview-images-via-3d-to-2d-queries.html) projects each 3D object-query reference point into every camera that can see it, then samples the corresponding multiscale features. [BEVFormer](/paper%20shorts/2022/03/31/bevformer-learning-birds-eye-view-representation-from-multi-camera-images-via-spatiotemporal-transformers.html) projects reference points generated by BEV queries._

Projection cannot recover detail that the image backbone has already removed. Fine feature maps preserve small or distant actors, while coarser maps provide larger receptive fields and scene context. The backbone decides which visual evidence remains available; calibration decides where a 3D hypothesis reads that evidence.

### LiDAR sparsity

The main LiDAR encoder decision is when to convert occupied 3D cells into a dense 2D map. [PointPillars](/paper%20shorts/2018/12/14/pointpillars-fast-point-cloud-encoders.html) groups points into vertical columns, pools each column, scatters the features into a dense pseudo-image, and runs most of the network as a 2D CNN. [SECOND](/paper%20shorts/2018/10/06/second-sparsely-embedded-convolutional-detection.html) keeps a sparse 3D middle encoder before compressing height. [DSVT](/paper%20shorts/2023/01/15/dsvt-dynamic-sparse-voxel-transformer.html) replaces sparse convolution in this stage with bounded attention. Both avoid computation at empty voxels while preserving 3D structure longer than PointPillars.

[![Animation comparing early densification in PointPillars, late BEV densification in SECOND and DSVT, and box prediction from active voxels in VoxelNeXt](/assets/images/autonomous-perception-lidar-encoder.gif)](/assets/images/autonomous-perception-lidar-encoder.gif)
_PointPillars collapses height early. SECOND and DSVT keep occupied 3D cells through more of the encoder, then build a dense BEV map for detection. [VoxelNeXt](/paper%20shorts/2023/03/20/voxelnext-fully-sparse-voxelnet-for-3d-detection-and-tracking.html) predicts directly from active voxels and avoids a dense detection heatmap._

These models place the dense conversion at progressively later stages. Early height collapse is efficient on mostly planar roads. Longer sparse 3D processing preserves stacked surfaces and height-dependent evidence, and a fully sparse head avoids allocating empty BEV output locations. Each active cell should also retain intensity, acquisition time, and point age because a rotating scan is collected while the ego vehicle and nearby actors are moving.

### Radar range and velocity

Radar provides range, radial velocity, Radar Cross Section, timestamp, and uncertainty, but its angular resolution and elevation estimates are weak, and multipath can create ghost returns. An encoder designed like a low-resolution LiDAR encoder can discard the attributes that make radar useful. Camera-radar models differ mainly in where radar first changes the camera computation.

[![Animation comparing camera-radar interaction at the proposal, depth, and BEV stages in CRAFT, CRN, and RCBEVDet](/assets/images/autonomous-perception-radar-encoder.gif)](/assets/images/autonomous-perception-radar-encoder.gif)
_[CRAFT](/paper%20shorts/2022/09/14/craft-camera-radar-3d-object-detection-with-spatio-contextual-fusion-transformer.html) begins with a camera proposal and associates a soft set of compatible radar returns in polar coordinates. [CRN](/paper%20shorts/2023/04/03/crn-camera-radar-net-for-3d-perception.html) intervenes earlier in geometry: radar changes the camera depth distribution before lifting, then deformable attention aligns the camera and radar BEV features. [RCBEVDet](/paper%20shorts/2024/03/25/rcbevdet-radar-camera-fusion-in-bev.html) gives radar a point path and a transformer path, constructs a radar-specific BEV, and then aligns it with camera BEV._

These methods use radar range at three different points: associating returns with an object, choosing depth along a camera ray, or constructing a separate metric field. Early rasterization can erase Doppler, confidence, and return-level correspondence. Radar encoding and camera-radar fusion therefore have to be designed together.

## Camera features to 3D

A pixel identifies a camera ray, not a distance along that ray. Camera-only 3D perception must supply the missing depth. [Lift, Splat, Shoot](/paper%20shorts/2020/08/13/lift-splat-shoot-encoding-images-from-arbitrary-camera-rigs.html) predicts a categorical depth distribution at every image location, lifts the image feature along its calibrated ray, and pools the resulting 3D features into BEV. [BEVDepth](/paper%20shorts/2022/06/21/bevdepth-acquisition-of-reliable-depth-for-multiview-3d-detection.html) uses the same construction but adds depth supervision from projected LiDAR during training.

![Figure 1 from Lift, Splat, Shoot, showing multiview evidence represented in vehicle-centered BEV](/assets/images/lift-splat-shoot-paper-figure-1.png)
_LSS converts perspective evidence from several cameras into one vehicle-centered metric grid. Source: [Lift, Splat, Shoot](/paper%20shorts/2020/08/13/lift-splat-shoot-encoding-images-from-arbitrary-camera-rigs.html), Figure 1._

Query-based methods start from a location in metric space and retrieve image evidence for it. [DETR3D](/paper%20shorts/2021/10/14/detr3d-multiview-images-via-3d-to-2d-queries.html) assigns an object query a reference point $(x,y,z)$, projects that point into the cameras, and samples nearby image features. BEVFormer assigns every BEV cell an $(x,y)$ location and samples several heights along its vertical pillar. It stores a dense metric field but retrieves only a small set of image features for each cell.

[![Animation comparing depth along an image ray in LSS, a 3D object-query reference point in DETR3D, and vertical reference points from a BEV cell in BEVFormer](/assets/images/autonomous-perception-camera-lifting.gif)](/assets/images/autonomous-perception-camera-lifting.gif)
_LSS predicts depth along an image ray. DETR3D predicts a 3D reference point for each object query. BEVFormer fixes the $(x,y)$ position of each BEV cell and samples several heights $z$._

The depth mechanism determines both compute and failure modes. LSS-style models evaluate many pixel-depth combinations, and a wrong depth distribution deposits features in the wrong BEV cells. DETR3D retrieves evidence only around a bounded set of object hypotheses, so an object can be missed when no query develops support for it. BEVFormer pays the memory cost of a dense BEV state while limiting the number of image samples used to update each cell.

| Representation | Natural outputs | Dominant cost | Characteristic miss |
| --- | --- | --- | --- |
| Lifted dense BEV | Occupancy, roads, maps, detection | Image locations × depth bins, then BEV area | Wrong depth commits evidence to the wrong cell |
| Object queries | Detection, tracking, motion | Queries × visible views × feature samples | Missing or poorly initialized object hypothesis |
| BEV queries | Dense scene state with sparse retrieval | BEV cells × projected samples | Weak support at the cell's reference points |

## Point, query, and BEV fusion

Fusion needs a representation that can carry evidence from every sensor. [PointPainting](/paper%20shorts/2019/11/22/pointpainting-sequential-fusion-for-3d-object-detection.html) projects camera class scores onto LiDAR returns before voxelization, so image semantics enter the model only at pixels with a LiDAR return. [FUTR3D](/paper%20shorts/2022/03/20/futr3d-unified-sensor-fusion-framework-for-3d-detection.html) uses one 3D reference point to sample camera, LiDAR, and radar features into an object query. [BEVFusion](/paper%20shorts/2022/05/26/bevfusion-multi-task-multi-sensor-unified-bev.html) encodes camera and LiDAR separately, converts both feature sets to dense BEV, and fuses the aligned maps.

[![Animation showing the same actor and lane evidence entering point, object-query, and dense-BEV fusion](/assets/images/autonomous-perception-fusion-granularity.gif)](/assets/images/autonomous-perception-fusion-granularity.gif)
_PointPainting keeps camera semantics only where LiDAR returns exist, so a lane cue without points disappears. FUTR3D gathers evidence around an actor hypothesis rather than representing the full background. BEVFusion preserves both the actor and the dense lane field._

The fusion representation determines which evidence reaches the task head. Point fusion is efficient when predictions should follow reliable returns, but it cannot carry image evidence where no point exists. Query fusion fits sparse outputs such as objects and tracks. Dense BEV fusion supports occupancy, maps, and other scene fields, but its compute grows with spatial area. [TransFusion](/paper%20shorts/2022/03/22/transfusion-robust-lidar-camera-fusion-with-transformers.html) uses LiDAR proposals to focus camera attention. [DeepInteraction](/paper%20shorts/2022/08/23/deepinteraction-3d-object-detection-via-modality-interaction.html) keeps separate modality streams and lets them update one another. [UniTR](/paper%20shorts/2023/08/15/unitr-unified-efficient-multimodal-transformer-for-bev.html) builds modality-specific tokens before applying shared transformer blocks. These designs share information while retaining sensor provenance.

![Figure 2 from BEVFusion, showing modality-specific encoders converging on a shared BEV and task-specific heads](/assets/images/bevfusion-unified-bev-paper-figure-2.png)
_BEVFusion's paper diagram makes the separation explicit: sensor-specific tokenization, a shared metric field, and task-specific outputs. Source: [BEVFusion](/paper%20shorts/2022/05/26/bevfusion-multi-task-multi-sensor-unified-bev.html), Figure 2._

## Training for missing and degraded sensors

A model trained with every sensor may fail when one stream disappears. [UniBEV](/paper%20shorts/2023/09/25/unibev-robust-multimodal-detection-with-uniform-bev-encoders.html) trains on complete and missing-modality inputs, then normalizes fusion over the streams that remain. [MetaBEV](/paper%20shorts/2023/04/19/metabev-solving-sensor-failures-for-bev-perception.html) lets BEV queries retrieve from whichever encoders are available and uses modality-specific experts. Both methods answer an availability question: did the stream arrive?

[![Animation contrasting modality availability in UniBEV and MetaBEV with reliability gating in Grace-BEV](/assets/images/autonomous-perception-modality-dropout.gif)](/assets/images/autonomous-perception-modality-dropout.gif)
_UniBEV and MetaBEV use the same availability mask for a healthy camera and a degraded camera because both streams are present. [Grace-BEV](/paper%20shorts/2026/05/29/grace-bev-graceful-degradation-under-sensor-failures.html) estimates reliability, allowing the model to reduce the weight of a corrupted camera while retaining healthy LiDAR._

A degraded sensor is harder because its stream is present but unreliable. Modality dropout teaches the network how to operate with a missing stream; it does not teach the network to recognize blur, glare, miscalibration, packet corruption, or plausible but incorrect returns. Degraded-sensor handling requires representative corruptions during training, a health or reliability signal that the model can observe, and a fusion rule that can reduce the sensor's contribution.

## Multi-task optimization

Detection, occupancy, lane estimation, velocity, and tracking can share image features and metric scene reasoning. Their losses, however, differ in units, label density, and convergence speed. [BEVFusion](/paper%20shorts/2022/05/26/bevfusion-multi-task-multi-sensor-unified-bev.html) uses a shared trunk with task-specific decoders. [UniAD](/paper%20shorts/2022/12/20/uniad-planning-oriented-autonomous-driving.html) also encodes task dependencies by passing tracking and map queries into motion, occupancy, and planning modules. In either case, joint training introduces three separate problems: loss scale, relative training rate, and gradient direction.

[![Animation applying Kendall uncertainty weighting, GradNorm, and PCGrad to the same pair of raw task gradients](/assets/images/autonomous-perception-multitask-gradients.gif)](/assets/images/autonomous-perception-multitask-gradients.gif)
_[Kendall et al.](/paper%20shorts/2017/05/19/multi-task-learning-using-homoscedastic-uncertainty.html) learn one uncertainty scale per task, changing its contribution through $\mathcal{L}_i/(2\sigma_i^2)+\log\sigma_i$. [GradNorm](/paper%20shorts/2017/11/07/gradnorm-adaptive-loss-balancing.html) changes task weights so shared-layer gradient norms track relative training rates. Both change magnitude without resolving a negative angle. [PCGrad](/paper%20shorts/2020/01/19/pcgrad-gradient-surgery-for-multi-task-learning.html) acts on direction: when two gradients conflict, it projects away the opposing component._

Each problem needs its own diagnostic. Normalize losses by meaningful counts before learning task weights; otherwise a dense prediction head can dominate because it contributes more terms. Measure each task's gradient norm at shared layers to find unequal training rates, and measure pairwise cosine similarity to find conflicting directions. Scalar weights can change gradient magnitude but cannot remove a directional conflict. Persistent conflicts may require gradient surgery, task adapters, alternating updates, or an earlier split in the network.

| Failure | Measurement | Intervention |
| --- | --- | --- |
| Loss scale | Normalized loss magnitude | Unit-aware normalization; uncertainty weighting |
| Training rate | Shared-layer gradient norm and relative loss decay | GradNorm |
| Gradient conflict | Pairwise gradient cosine similarity | PCGrad, adapters, or partial separation |

## Training-only LiDAR

LiDAR can play three different roles in depth learning. In [BEVDepth](/paper%20shorts/2022/06/21/bevdepth-acquisition-of-reliable-depth-for-multiview-3d-detection.html), projected LiDAR supplies camera-depth labels during training and is absent at inference. In [Sparse-to-Dense](/paper%20shorts/2017/09/21/sparse-to-dense-depth-prediction-from-sparse-depth-and-rgb.html), sparse depth is an input during both training and deployment, so the model still depends on a depth sensor. In [CRKD](/paper%20shorts/2024/06/17/crkd-camera-radar-distillation-from-lidar-camera.html), a camera-LiDAR teacher transfers feature, relation, and response knowledge to a camera-radar student; deployment uses only the student.

[![Animation separating LiDAR depth labels, runtime sparse-depth input, and a LiDAR-camera teacher](/assets/images/autonomous-perception-lidar-training-contracts.gif)](/assets/images/autonomous-perception-lidar-training-contracts.gif)
_BEVDepth removes LiDAR after it supervises the camera depth distribution. Sparse-to-Dense keeps sparse depth in the runtime graph. CRKD removes the LiDAR teacher but retains the camera-radar student. The three systems use LiDAR at different stages._

The runtime graph and the label-generation graph should be documented separately. Offline supervision may use LiDAR, future frames, repeated passes, larger teacher models, or human review. Projected LiDAR labels also need visibility checks, pose interpolation, uncertainty handling, and ignore regions. Calibration error, occlusion, timestamp mismatch, and object motion can place a return on the wrong image region.

## Temporal state

A temporal model must specify what state crosses the frame boundary. [BEVDet4D](/paper%20shorts/2022/03/31/bevdet4d-temporal-cues-in-multicamera-3d-detection.html) warps the previous camera-BEV feature into the current ego frame and fuses it with the current feature. BEVFormer recurrently updates a dense field of BEV queries. Dense state preserves road layout, free space, background, and weak evidence that has not yet formed an object hypothesis, but memory grows with BEV area and retained history. Ego-motion alignment corrects the coordinate frame for static structure; moving actors still require the model to estimate their motion.

[![Animation comparing a warped dense BEV field, transformed recurrent instances with fresh anchors, and a bounded foreground-query queue](/assets/images/autonomous-perception-temporal-memory.gif)](/assets/images/autonomous-perception-temporal-memory.gif)
_The left column carries every BEV cell. [Sparse4D v2](/paper%20shorts/2023/05/23/sparse4dv2-recurrent-temporal-fusion-with-sparse-model.html) transforms prior instances into the current frame and adds fresh anchors for new objects. [StreamPETR](/paper%20shorts/2023/03/21/streampetr-object-centric-temporal-modeling-for-multiview-3d-detection.html) keeps a FIFO memory of top foreground queries, transforms their reference points with ego pose, discards background queries, and adds fresh queries. Sparse recurrence bounds memory, but it must explicitly manage births, aging, and stale state._

[SOLOFusion](/paper%20shorts/2022/10/05/solofusion-temporal-multiview-3d-object-detection.html) combines short, high-resolution stereo for fine correspondence with a longer, low-resolution BEV history for depth and velocity. [SparseBEV](/paper%20shorts/2023/08/18/sparsebev-high-performance-sparse-3d-object-detection.html) keeps sparse object support but reads from several stored timestamps, so retrieval cost still grows with history length. Sparse temporal models may either compress the past into recurrent state or retain past features and access them sparsely. These choices have different memory and latency costs.

![Figure 3 from StreamPETR, showing object queries propagated through a temporal memory queue](/assets/images/streampetr-paper-figure-3.png)
_StreamPETR carries selected foreground query state instead of a sequence of full scene grids. Source: [StreamPETR](/paper%20shorts/2023/03/21/streampetr-object-centric-temporal-modeling-for-multiview-3d-detection.html), Figure 3._

Dense and sparse memory fail in different ways. A dense field preserves context that may later support a new detection, but it allocates capacity to the full scene. Sparse state is efficient after an actor has been detected, but discarded background evidence cannot contribute until a new query is created. A deployed recurrent model also needs explicit rules for state age, observation freshness, confidence, object birth, and reset behavior. The cited methods define learned temporal updates; they do not by themselves define a complete policy for sensor outages or stale state.

## Sparse computation costs

Sparse LiDAR encoders avoid computation in empty 3D space, and sparse camera detectors avoid updating every BEV cell. These savings apply only to the modules made sparse. Surround-camera backbones still process every image at several scales. Sparse operators also introduce indexing, sorting, padding, and irregular memory access, so their actual speed depends on the accelerator, kernels, and compiler.

The cited papers remove different dense terms. [VoTr](/paper%20shorts/2021/09/06/votr-voxel-transformer-for-3d-object-detection.html), [SST](/paper%20shorts/2021/12/13/sst-single-stride-sparse-transformer-for-3d-detection.html), and DSVT bound interactions among occupied LiDAR voxels. VoxelNeXt removes the dense LiDAR detection head. Sparse4D v2 and StreamPETR bound recurrent object state. SparseBEV replaces a full camera-BEV field with learned pillar support points. FLOPs do not capture synchronization and memory traffic, so evaluation should include per-component latency, peak memory, P95/P99 end-to-end latency, and recall in dense scenes.

## Pretraining targets

Image-classification pretraining teaches visual appearance but does not directly teach calibration, cross-view correspondence, metric depth, ego motion, or temporal persistence. [UniM²AE](/paper%20shorts/2023/08/21/unim2ae-multimodal-masked-autoencoders-with-unified-3d-representation.html) masks camera patches and LiDAR voxels, maps the visible features into a shared 3D volume, and reconstructs both modalities. [BEV-MAE](/paper%20shorts/2022/12/12/bev-mae-bird-eye-view-masked-autoencoders-for-point-cloud-pretraining.html) masks vertical LiDAR columns and predicts normalized point coordinates and density, matching the structure of outdoor point clouds.

[UniWorld](/paper%20shorts/2023/08/14/uniworld-autonomous-driving-pretraining-via-world-models.html) predicts current and future 4D occupancy. [ViDAR](/paper%20shorts/2023/12/29/vidar-visual-point-cloud-forecasting-for-autonomous-driving.html) predicts future point clouds from image history. [DriveWorld](/paper%20shorts/2024/05/07/driveworld-4d-pretrained-scene-understanding.html) separates dynamic memory from propagated static state. A longer prediction horizon does not necessarily provide better supervision: motion uncertainty, occlusion, pose error, and multiple valid futures make distant targets increasingly ambiguous. Pretraining should be judged by transfer across tasks, sensor configurations, and label budgets.

| Pretraining target | Learned relation | Main limitation |
| --- | --- | --- |
| Masked camera and LiDAR reconstruction | Cross-modal correspondence | Local correlated evidence can make reconstruction easy |
| Current occupancy | Metric scene structure | Requires geometric labels or a teacher |
| Future occupancy or point clouds | Motion and persistence | One target cannot represent every valid future |
| Teacher features and pseudo-labels | Task-specific abstractions | Inherits teacher errors and blind spots |

## Driving foundation models

The architectures above use a shared scene representation followed by specialized task heads. Waymo has described a broader model that shares more computation across perception, prediction, and driving. In [Waymo Co-CEO Dmitri Dolgov's talk, “The Demo Is Only 1% Of The Work”](https://www.youtube.com/watch?v=Gp4zrV3-6N8), the Waymo Foundation Model contains a Sensor Fusion Encoder, a Driving VLM, and a Generative World Decoder. The diagram proposes a path from multimodal sensor evidence to a shared world representation and then to actions and predictions. It does not establish that every displayed block runs unchanged in Waymo's deployed online controller.

![The Waymo Foundation Model diagram with sensor fusion, a driving VLM, and a generative world decoder](/assets/images/waymo-foundation-model-architecture.png)
_Figure: The Waymo Foundation Model architecture shown in [Dmitri Dolgov's Waymo talk](https://www.youtube.com/watch?v=Gp4zrV3-6N8). Screenshot supplied for this post; see Waymo's public [architecture description](https://waymo.com/blog/2025/12/demonstrably-safe-ai-for-autonomous-driving/) and earlier [foundation-model overview](https://waymo.com/blog/2024/10/ai-and-ml-at-waymo/)._

The three blocks have different roles:

| Path | Input → intermediate representation | Output role |
| --- | --- | --- |
| Sensor Fusion Encoder | Camera, LiDAR, radar → objects and sensor embeddings | Fast, metric evidence and reactions |
| Driving VLM | Text prompts, sensor data, and autonomous-driving history → VLM embeddings, semantics, rationales, and text tokens | Slower semantic reasoning for rare or complex situations |
| Generative World Decoder | Both representations → a shared world model | Driving actions, agent predictions, and other predictions |

The VLM does not replace the sensor stack. The sensor-fusion encoder preserves metric geometry and latency-sensitive evidence. The VLM contributes language-conditioned semantics and broader learned context on a slower path, reflected by the diagram's “thinking fast, thinking slow” annotation. The decoder must combine both representations before producing actions or predictions; language output is not sent directly to steering.

A generative world decoder expands the training target beyond the current scene. It can predict how agents and the environment may evolve, generate candidate actions, or produce signals used to evaluate those actions. Waymo's public description says its World Decoder predicts road-user behavior, generates maps and vehicle trajectories, and provides trajectory-validation signals. It also describes adapting large teacher models to the Driver, Simulator, and Critic before distilling smaller students. These statements clarify the slide's “versatile” and “multi-stage training” labels, but they do not reveal the exact online computation graph or demonstrate closed-loop safety by themselves.

This design still depends on the earlier interfaces. Sensor-specific encoders preserve measurements, calibration places them in metric space, and temporal state carries evidence across time. The foundation model adds a reusable route for semantics, prediction, and action. [Vision-Language Models: A Reading Guide](/blog/2026/07/05/from-seeing-to-doing-the-evolution-of-vision-language-models.html) covers the related progression from image-text alignment to grounding, video, and action. In the Waymo diagram, the VLM contributes semantic context, the sensor-fusion encoder contributes calibrated scene evidence, and the shared decoder combines them to predict future states and driving behavior.

The unresolved question is whether one decoder can remain grounded in metric sensor evidence, use slower language-level reasoning when it helps, represent multiple possible futures, and still satisfy the latency and validation requirements of closed-loop driving.

## Design checklist

1. Preserve what each sensor uniquely measures before converting it: camera appearance, LiDAR geometry, and radar range, velocity, and uncertainty.
2. State which variable chooses 3D location: image depth, an object query, or a BEV cell with height samples.
3. Choose the fusion representation from the output: points for point-aligned evidence, queries for actors, and dense BEV for scene fields.
4. Train every supported sensor configuration, and separate availability from reliability.
5. Diagnose loss scale, training rate, and gradient direction separately.
6. Document runtime inputs, label sources, and teacher models as different graphs.
7. Name what crosses the frame boundary and define birth, age, freshness, and reset behavior.
8. Profile the executed system; sparsity in one module does not make the full pipeline sparse.

A perception model should make three boundaries explicit: what each sensor encoder preserves, how features enter a calibrated metric representation, and what state persists across frames. Once those boundaries are clear, architectural comparisons become concrete: each paper changes a specific representation, correspondence rule, supervision path, or compute term.
